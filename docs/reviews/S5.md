## Bloquant

### B1. La liste dévoile la note solveur et les techniques avant la partie
- **Où** : `web/src/lab/list.ts:16-17` (colonnes Note, Étapes, Techniques, Perçue), `:51-53` (cellules), `:68` (« Note solveur » dans le panneau), filtre « Note » `:81` ; `web/src/lab/keep.ts:34,37` ; `lab/lab_server.py:144-147` (`/api/candidates` renvoie `rating`, `techniques`, `trace_summary`).
- **Scénario** : le joueur ouvre le labo, voit « Note 3 » et les techniques de la candidate 3, puis clique « Jouer à l'aveugle ». Sa note perçue est biaisée, le calibrage S5.3 perd sa valeur. La colonne « Perçue » montre aussi la note de l'autre joueur avant qu'il ait joué. Capture : `list-1280.png`.
- **Origine** : l'en-tête de `list.ts` l'assume (« The table shows the solver measures »), et la consigne S5.1 demandait les techniques dans la liste. C'est contradictoire avec la règle « rien avant la fin de partie, liste comprise » : décision humaine à prendre.
- **Correction proposée** : aveugle par joueur. Pour une candidate que le joueur courant n'a pas terminée (pas de partie ni de note perçue), masquer note, techniques, étapes et perçue des autres (« ? ») ; le serveur ne les renvoie qu'avec `?player=` et une partie enregistrée. Prévoir un interrupteur « mode création » explicite si l'humain veut trier un lot sans y jouer.

### B2. Grille résolue enregistrée « abandoned » si l'on quitte par le lien du jeu
- **Où** : `web/src/lab/play.ts:54` (`post(true)` dans le nettoyage) ; `web/src/lab/logic.ts:139` (`abandoned || !solved`).
- **Scénario, reproduit dans Chrome** : résoudre `demo:1` ; le jeu affiche « Programme bouclé » et son bouton « Accueil », plus visible que « Terminer » dans le bandeau du labo (`play-solved-1280.png`). Un clic sur « Accueil » (ou sur « ‹ Accueil », ou sur l'onglet « Lot ») enregistre `"outcome": "abandoned"` et saute l'écran de fin : pas de note perçue.
- **Correction proposée** : dans le nettoyage, `post(!rec.solved)`, et après une résolution, aller à `#/fin/...` quel que soit le chemin de sortie. Mieux : une option de `GameContext` pour masquer, dans le labo, le lien retour et les boutons de fin du jeu (`game.ts:271-276`).

### B3. Rechargement ou fermeture en cours de partie : rien n'est enregistré
- **Où** : `web/src/lab/play.ts:51-55` (enregistrement de l'abandon seulement au changement de hash) ; en-tête `play.ts:6`, qui annonce le contraire.
- **Scénario, reproduit** : partie `demo:2`, 3 s, F5 → 0 ligne ajoutée, minuteur à 00:00, plateau vide. Fermeture de l'onglet → 0 ligne. La partie relancée a l'air d'une première partie, alors que le joueur connaît déjà une partie de la solution : temps faussé.
- **Correction proposée** :
  - sur `pagehide`, envoyer l'abandon avec `navigator.sendBeacon` (Blob JSON) ;
  - ou mieux, garder la partie en cours côté serveur : `POST /api/sessions` au début avec `started`, mise à jour de l'état, reprise au rechargement ;
  - marquer `resumed: true` ou un numéro de tentative dans la ligne.

## À corriger

### C1. Changement de joueur en pleine partie : note perçue attribuée au mauvais joueur
- **Où** : `web/src/lab/end.ts:16,26,57` utilise `ctx.player` et non `rec.player` ; le sélecteur reste actif pendant la partie (`main.ts:48-53`).
- **Scénario, reproduit** : Joueur 1 lance `demo:2`, clique « Joueur 2 », abandonne. La partie est enregistrée pour Joueur 1, mais l'écran de fin affiche Joueur 2 et range la note perçue sous `{"Joueur 2": 4}`.
- **Correction** : figer le sélecteur pendant `#/partie` ; sur l'écran de fin, prendre `rec.player`.

### C2. Le temps compte l'onglet masqué
- **Où** : `web/src/lab/logic.ts:118-133` (horloge murale `Date.now`).
- **Scénario, reproduit** : document masqué 3 s → le minuteur passe de 00:00 à 00:03, et `ms` les inclura.
- **Correction** : suspendre sur `visibilitychange` ; enregistrer `ms` (temps actif) et `wall_ms` ou `hidden_ms`.

### C3. `plays.jsonl` peu exploitable pour le calibrage (S5.3)
- **Où** : `lab/lab_server.py:196-203`, `:304-311`.
- **Manques** :
  - rien ne lie une ligne à la grille jouée : relancer un lot sous le même nom écrase `candidates/<lot>.json` (`start_generation` ne refuse qu'un lot *en cours*), et parties comme notes (`lot:index`) pointent alors vers une autre grille ;
  - la note perçue n'est pas dans la ligne : elle vit dans `notes.json`, une par joueur, écrasée à chaque partie ;
  - pas de numéro de tentative (rejouer une grille connue fausse temps et erreurs) ;
  - `ts` est l'heure de fin, pas de début ;
  - pas de version du format.
- **Correction** :
  - refuser un nom de lot existant (409) ;
  - ajouter `grid_hash` (sha1 de la grille sans `lab`), `attempt`, `started` et `schema: 1` ;
  - enregistrer la note perçue avec la partie (`PATCH /api/plays/<id>` depuis l'écran de fin) ;
  - documenter le format (champ par champ) dans le skill ou un `lab/README`.

### C4. La note perçue reste modifiable après la révélation
- **Où** : `web/src/lab/end.ts:52-59`. Après « Valider et révéler », les boutons 1-4 et « Valider » restent actifs et réécrivent `felt` (`end-revealed-1280.png`).
- **Correction** : figer la note une fois révélée, ou ne garder que la première pour le calibrage (cf. C3).

### C5. La promotion reformate tout `grids.json`
- **Où** : `lab/lab_server.py:89-92` (`indent=1`), appelé `:298`.
- **Constat** : `grids.json` est en `indent=2` (aller-retour `json.dumps(..., ensure_ascii=False, indent=2)` identique à l'octet près) ; après une promotion, chaque ligne du fichier change dans le diff.
- **Correction** : `indent=2` pour `grids.json`, et un test d'aller-retour.

### C6. Le serveur accepte les écritures d'une autre origine (CSRF)
- **Où** : `lab/lab_server.py:346-354` (aucun contrôle de `Content-Type` ni d'`Origin`).
- **Scénario, reproduit** : `curl -X POST -H 'Content-Type: text/plain' -H 'Origin: https://evil.example' .../api/plays -d '{...}'` → 200, ligne écrite. N'importe quelle page ouverte dans le navigateur peut ainsi écrire des parties, lancer une génération (CPU) ou promouvoir une grille.
- **Correction** :
  - exiger `Content-Type: application/json` sur POST et PUT, ce qui force une prévalidation CORS à laquelle le serveur ne répond pas ;
  - refuser un `Origin` hors `http://localhost:5173` et `http://127.0.0.1:5173` ;
  - vérifier `Host` contre le rebinding DNS ; le proxy Vite garde `Host: localhost:5173`.

### C7. Le générateur numérote à partir de 0 : `id` 0 et « Candidate 0 »
- **Où** : `dispatch_solver/generate/lot.py:280` (`index=len(kept)`, `id = index + 1`) ; `lab/lab_server.py:161` (`g["id"] = index`) ; `lab/candidates/demo.json` commence à 1, donc les tests ne le voient pas.
- **Scénario, reproduit** : lot `t1` généré, `/api/grid/t1/0` renvoie `id: 0`, refusé par `validateGrid()` (`id: positive integer expected`). Le jeu ne valide pas et la partie se joue, mais l'écran affiche « Candidate 0 » (`play-generated-1280.png`).
- **Correction** : garder l'`id` du générateur pour la grille aveugle, afficher `index + 1`, aligner `demo.json` sur le générateur (base 0) et ajouter un test.

### C8. Deux bulletins peuvent avoir la même date de publication
- **Où** : `lab/lab_server.py:273-278` (n° et id contrôlés, pas la date).
- **Scénario, reproduit** : promotion de `demo:4` au 2026-11-22, déjà prise par la grille 12 → 200. Deux « bulletins du jour » pour la même date.
- **Correction** : 409 sur une date déjà prise. Option : refuser un numéro plus petit avec une date plus tardive.

### C9. La promotion ne vérifie pas `matches_reference`
- **Où** : `lab/lab_server.py:295`.
- **Constat** : `check_published`, lancé par la CI via `check_unique.py`, exige `compositions == 1`, `matches_reference` et `deduction == "solved"` ; le labo ne regarde que les deux derniers. Une grille dont la `solution` ne correspond pas à la composition unique passerait la promotion puis casserait la CI.
- **Correction** : ajouter `report.get("matches_reference")` à la condition.
